# STM32G431 单分区 Bootloader

本项目使用 STM32G431RBTx 的 USART2 和自定义 `0x10`/`0xAA` 协议进行单分区固件升级。串口使用 DMA 接收，镜像通过 CRC 和 SHA-256 检查，并在验证成功后写入有效记录。

> **重要：只有一个 APP 分区。** 开始升级会使旧 APP 的有效记录失效并擦除 APP；升级失败或断电后需要重新完整升级，不支持回滚。SHA-256 只检查完整性，不验证固件来源。

## 目录和使用

| 路径 | 用途 |
| --- | --- |
| `bootloader/Core/Src/main.c` | 外设初始化与主循环 |
| `bootloader/app/modbus.c`、`modbus.h` | 纯协议解析、CRC 计算、应答组帧 |
| `bootloader/app/modbus_port.c`、`modbus_port.h` | USART2 DMA 接收、队列、超时和应答发送 |
| `bootloader/app/upgrade.c`、`upgrade.h` | 升级状态机、包校验及启动判断 |
| `bootloader/app/upgrade_flash.c` | Flash 擦除、写入和读取 |
| `bootloader/app/upgrade_platform.c` | 跳转 APP 的平台处理 |
| `bootloader/app/error_trace.c`、`error_trace.h` | Error_Handler 首次错误的来源、编号及返回值记录 |
| `bootloader/app/boot_log.h` | USART1 升级日志开关及输出接口，实现位于 modbus_port.c |
| `STM32_OTA_PC/` | 串口升级、镜像制作和 SWD 烧录上位机 |
| `tests/` | 固件模拟测试 |

上位机的安装和使用方法见 [上位机 README](STM32_OTA_PC/README.md)，固件布局和约定另见 [UPGRADE.md](bootloader/app/UPGRADE.md)。

调试时进入 `Error_Handler()`，可在对应工程的 Keil Watch 中展开 `g_error_trace`，查看错误编号、原因、文件、函数、行号及返回值。编号表和定位步骤见 [ERROR_TRACE.md](bootloader/app/ERROR_TRACE.md)。

USART2 默认 **1000000 波特、8N1**，PA2 为 TX、PA3 为 RX，PA1 为 RS-485 方向控制（高发送、低接收）。Bootloader、APP 和上位机统一使用站号 3（`0x03`）。

升级日志独立从 **USART1（PB6 TX，PB7 RX，115200、8N1）** 输出，以 `[BOOT]` 开头。接 USB-TTL 的 RX 到 PB6、共地即可观察；日志不发送到 USART2/RS-485。包含启动检查、查询/控制命令、擦除结果、包号、累计写入字节、ACK、SHA-256、有效记录保存及跳转 APP。`boot_log.h` 中 `BOOT_LOG_ENABLED=0` 可关闭日志。实现不使用 printf，只在普通上下文输出；USART1 发送失败仅累计 `boot_log_drops`，不阻断 OTA。

## Flash 布局和镜像

| 地址范围 | 大小 | 用途 |
| --- | ---: | --- |
| `0x08000000–0x080037FF` | 14 KiB | Bootloader |
| `0x08003800–0x08003FFF` | 2 KiB | Bootloader 数据页与 APP 有效记录 |
| `0x08004000–0x080043FF` | 1 KiB | 版本区 |
| `0x08004400–0x080047FF` | 1 KiB | SHA-256 摘要区 |
| `0x08004800–0x0801FFFF` | 110 KiB | APP，最多 112,640 字节 |

- OTA 镜像按顺序为：**1 KiB 版本区 + 1 KiB 摘要区 + 原始 APP**。版本由上位机按 UTF-8 编码，剩余补 `0x00`；摘要区前 32 字节是原始 APP 的 SHA-256，其余由上位机补 `0x00`。
- SHA-256 的计算范围恰好是从 `0x08004800` 开始的原始 APP 字节，不包含版本区、摘要区或 Flash 写入时末尾的补齐字节。
- `0x08003800` 起的有效记录是两个**小端** 32 位数：魔数 `0x53484132` 和原始 APP 长度。无有效记录、APP 向量无效或摘要不匹配均不会启动 APP。
- APP 必须链接到 `0x08004800`，且 `SystemInit` 不能把 VTOR 改回 Bootloader 的向量表地址。
- 工厂烧录除了 Bootloader 和 APP，还必须包含版本区、摘要区和有效记录。上位机可生成完整 128 KiB 的工厂 BIN 或 HEX；空白处填 `0xFF`。工厂镜像不是 OTA 镜像，不能用于串口升级。

## 固件运行流程

1. 外设初始化完成后，`Modbus_StartReceive()` 启动 USART2 DMA 接收；`Upgrade_Init()` 读取有效记录，检查 APP 的长度、向量和 SHA-256，并设置空闲或损坏状态。
2. 主循环先调用 `modbusdeal()` 消费 DMA 数据、拼帧、校验 CRC16 并发送已排队应答，再调用 `Upgrade_Poll()`。后者通过 `switch/case` 分别处理等待、握手、接收和启动 APP 四个状态，共用接收队列按顺序处理控制帧和数据帧。
3. 上电进入等待状态。如果 APP 有效且约 4 秒内没有进入握手，设备会在通信空闲时再次检查镜像并跳转 APP。等待时间由 `upgrade.h` 中的 `UPGRADE_BOOT_WAIT_MS` 设置。查询会使等待状态进入握手，不再按该上电等待定时器自动跳转。
4. 设备没有有效 APP 时留在 Bootloader，并约每 100 ms 排队发送一次状态 `0x0055` 的查询格式主动上报；实际发送仍需等待总线空闲。
5. 收到开始升级命令后，固件暂停接收，先擦除有效记录页，再擦除版本区、摘要区和唯一 APP 区。擦除成功后恢复接收、保存会话 key、进入接收状态并返回控制确认；擦除失败则返回查询格式状态应答。
6. 固件按包校验会话 key、协议版本、包号、CRC32、长度和版本区零填充，再写入 Flash 并回复对应包号的应答。
7. 末包写入后，检查 APP 栈指针、复位向量和 SHA-256；通过后写入有效记录，再回复末包成功。应答发送完成、通信空闲且镜像再次校验通过后跳转 APP。

Flash 以 8 字节为单位编程：非末包尾部不足 8 字节时暂存在 RAM，下一包到来后继续写入；末包不足 8 字节的尾部补 `0xFF` 写入。因此非末包成功应答不保证暂存的尾部已经持久化。末包成功应答表示校验通过且有效记录已写入，但**不表示 APP 已成功运行**。

## 协议约定

本协议借用了 Modbus CRC16，但 `0x10` 和 `0xAA` 的帧格式为项目自定义格式，不能直接当作标准 Modbus 功能码处理。

- 设备地址：`0x03`；控制寄存器起始地址：`0x00E6`；协议版本：`0x0001`。
- 新增自定义 `0x11` 版本分块查询（每块最多 32 字节），同时返回 Bootloader/APP 运行模式；上位机支持重启并查询 OTA、数字版本递增压力测试和分卷日志。协议及完整使用流程见 [上位机 README](STM32_OTA_PC/README.md)。
- 除 CRC16 外，多字节协议字段和 CRC32 均为**大端**；帧末 CRC16/MODBUS 为**低字节在前**。
- CRC16 覆盖除帧末 CRC16 自身之外的所有字节，初值 `0xFFFF`、反射多项式 `0xA001`。
- 数据包 CRC32 仅覆盖该包的载荷；使用标准 CRC-32（初值 `0xFFFFFFFF`、反射多项式 `0xEDB88320`、结果异或 `0xFFFFFFFF`）。
- 主机须等待开始确认，以及每个数据包对应包号的成功应答；超时不得盲目自动重传。擦除期间设备暂停接收，过早发送的数据可能丢失。

### 查询状态：`0x10`

查询请求和状态应答均为 14 字节：

| 字段 | 字节数 | 请求值 | 应答值 |
| --- | ---: | --- | --- |
| 设备地址 | 1 | `03` | `03` |
| 功能码 | 1 | `10` | `10` |
| 寄存器起始地址 | 2 | `00 E6` | `00 E6` |
| 寄存器数量 | 2 | `00 03` | `00 03` |
| 状态 | 2 | 上位机固定 `00 00` | 当前 OTA 状态 |
| key | 4 | 上位机固定 `00 00 00 00` | 当前会话 key |
| CRC16 | 2 | 帧校验 | 帧校验 |

例如，查询请求：

```text
03 10 00 E6 00 03 00 00 00 00 00 00 E5 A2
```

设备空闲且当前 key 为 0 时的应答：

```text
03 10 00 E6 00 03 00 01 00 00 00 00 D8 62
```

| 状态值 | 含义 |
| --- | --- |
| `0x0000` | 禁止升级 |
| `0x0001` | 空闲，已有有效 APP 或升级成功 |
| `0x0002` | 正在接收升级数据 |
| `0x0003` | Flash 操作中 |
| `0x0055` | 当前 APP 无效或损坏 |

**注意：** 主动损坏状态上报与查询应答格式相同。因帧中没有请求序号，收到查询格式状态帧不能证明它一定是刚发出查询的响应。开始升级失败时固件也会发送查询格式状态帧；上位机在等待开始确认时如果先收到状态帧，会停止升级并提示重新查询，而不会把它视为开始成功。

### 控制命令：`0x10`

控制请求共 20 字节：

| 字段 | 字节数 | 值或含义 |
| --- | ---: | --- |
| 设备地址 / 功能码 | 1 + 1 | `03 10` |
| 寄存器起始地址 | 2 | `00 E6` |
| 寄存器数量 | 2 | `00 04` |
| 数据长度字段 | 4 | `00 00 00 08` |
| 状态字段 | 2 | 上位机固定 `00 01` |
| key | 4 | 开始升级时为本次会话 key |
| 操作码 | 2 | 见下表 |
| CRC16 | 2 | 帧校验 |

控制确认共 8 字节，固定格式为 `03 10 00 E6 00 04 21 DF`，不含操作码和 key：

| 操作码 | 功能 | 固件应答与动作 |
| --- | --- | --- |
| `0x0000` | 无操作 | 返回控制确认 |
| `0x0001` | 开始升级 | 擦除成功返回控制确认；擦除失败返回查询格式状态帧 |
| `0x0002` | 重启 | 返回控制确认，发送完成后复位 |
| `0x0003` | 回滚请求 | 本项目不支持回滚，返回查询格式状态帧，不恢复旧 APP |

上位机当前提供查询、开始升级和重启，不提供回滚按钮；开始升级时生成随机 32 位 key，后续数据包必须使用相同 key。该 key 用于会话匹配，**不是安全认证**。

例如，以 `0x12345678` 为 key 开始升级：

```text
请求：03 10 00 E6 00 04 00 00 00 08 00 01 12 34 56 78 00 01 71 4C
成功：03 10 00 E6 00 04 21 DF
```

以 key 0 重启：

```text
请求：03 10 00 E6 00 04 00 00 00 08 00 01 00 00 00 00 00 02 12 6A
应答：03 10 00 E6 00 04 21 DF
```

### 升级数据：`0xAA`

| 字段 | 字节数 | 含义 |
| --- | ---: | --- |
| 设备地址 / 功能码 | 1 + 1 | `03 AA` |
| 帧总长度 | 2 | 载荷长度 + 22 |
| 协议版本 | 2 | `00 01` |
| key | 4 | 必须与开始升级时相同 |
| 载荷长度 | 2 | 1～1024 字节 |
| 末包包号 | 2 | 总包数减 1 |
| 当前包号 | 2 | 从 0 开始递增 |
| 载荷 | 1～1024 | OTA 镜像对应的数据 |
| CRC32 | 4 | 本包载荷的 CRC32 |
| CRC16 | 2 | 整帧 CRC16 |

例如共有 3 包时，末包包号为 2，当前包号依次为 0、1、2。上位机每次最多发送 1024 字节载荷，收到对应包成功应答后再发送下一包。

数据应答共 7 字节：

```text
03 AA | 应答码(1) | 当前包号(2) | CRC16(2)
```

例如第 0 包写入成功：`03 AA 01 00 00 10 18`。

| 应答码 | 含义 |
| --- | --- |
| `0x01` | 当前包接收成功；末包还表示最终校验和有效记录写入成功 |
| `0x02` | 数据包 CRC32 错误，或末包 APP 向量/SHA-256 校验失败 |
| `0x03` | 接收帧超时或帧过短 |
| `0x04` | 协议版本错误 |
| `0x05` | 不在接收状态或会话 key 错误 |
| `0x06` | 包号不连续或超出末包包号 |
| `0x07` | 数据帧 CRC16 错误 |
| `0x08` | 长度不合法、超过分区或版本区填充不合法 |
| `0x09` | Flash 写入或有效记录保存失败 |

这些应答依赖设备能够识别帧和包号；噪声、队列溢出或无法识别的帧不保证收到应答。

## 上位机升级和异常处理

1. 选择已打包 OTA 镜像，或选择链接到 `0x08004800` 的原始 APP BIN 并填写版本。原始 APP 在升级前由上位机自动在内存中打包；也可手动生成 OTA 文件。
2. 连接串口，设备上电后及时查询；上位机会检查镜像长度、APP 向量和 SHA-256，在界面内确认固件类型和单分区擦除风险后开始升级。日志显示发送、接收的 HEX 数据以及解析的状态和应答。
3. 上位机先查询状态，再发送开始命令；开始确认默认等待最多 30 秒，数据包应答默认等待最多 8 秒。
4. 上位机逐包等待对应包号的成功应答并更新进度；遇到错误应答、串口错误或超时即停止，不自动重传。若升级已开始，旧 APP 可能已被擦除，需要重新开始完整升级。
5. 进度到 100% 只代表末包已确认。应在实际硬件上另外验证 APP 启动与功能。

SWD 工厂烧录需要单独安装 pyOCD 和 STM32G431 设备包；上位机要求选择下载器并确认，检查芯片 ID 和 Flash 容量，写入后读回完整 128 KiB 进行比较。具体步骤和注意事项见 [上位机 README](STM32_OTA_PC/README.md)。
